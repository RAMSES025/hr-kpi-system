## 2. Архитектурные решения

| Решение | Детали |
|---|---|
| Backend | FastAPI — REST-эндпоинты (`/users/`, `/users/{id}/absences/` и т.д.) **плюс** серверный рендеринг веб-интерфейса через Jinja2 (`/dashboard/{id}`, `/admin`) в одном приложении |
| ORM / БД | SQLAlchemy ORM (`models.py`, `database.py` — `SessionLocal`, `engine`). Конкретный движок БД (SQLite/PostgreSQL/др.) в диалоге не уточнялся — см. `database.py`. Миграций (Alembic и т.п.) не используется — таблицы создаются автоматически через `models.Base.metadata.create_all(bind=engine)` при старте |
| Фронтенд | Server-side HTML + Bootstrap 5.3.0 (CSS и JS-бандл подключены отдельно — забыть JS-бандл ломает модалки, уже наступали на эти грабли) |
| Паттерн форм | Post/Redirect/Get: веб-формы шлют `POST` на `/web/...` роуты, роут делает изменение в БД и возвращает `RedirectResponse` (303) на страницу отображения — без AJAX |
| Передача ошибок между роутами | Через query-параметры redirect'а (`/admin?error=insufficient_balance&err_user=...`), а не через сессии/flash-сообщения. Простое решение, но при росте числа сценариев ошибок может стать неудобным |
| Обновление типизированных/Enum-колонок | Устоявшаяся конвенция: `db.query(Model).filter(...).update({...})` с обычными строками вместо прямого присваивания атрибутов ORM-объекта — так Pylance не путается с типами `Enum`/`Column` |
| Необязательные параметры роутов | Явно типизируются как `Optional[str] = None`, `Optional[int] = None` (а не голое `str = None`) — тоже ради согласия с Pylance |
| Авторизация | **Отсутствует.** `user_id` передаётся напрямую в URL, входа по логину/паролю нет. Это осознанный временный компромисс для этапа разработки, не для продакшена |

## 3. Модули и их API

### 3.1 Сотрудники (`User`)
| Метод/роут | Назначение | Вход | Выход |
|---|---|---|---|
| `POST /users/` | Создать сотрудника (API) | JSON: `UserCreate` (ФИО, email, пароль, роль, оклад, макс. премия) | `UserResponse` |
| `GET /users/` | Список сотрудников (API) | `skip`, `limit` (query) | `List[UserResponse]` |
| `POST /admin/add-user` | Создать сотрудника (веб-форма из админки) | form: `full_name`, `email`, `password`, `base_salary`, `max_bonus` | redirect → `/admin` |

### 3.2 Учёт времени (`TimeLog`)
| Метод/роут | Назначение | Вход | Выход |
|---|---|---|---|
| `POST /users/{user_id}/clock-in/` | Отметить начало рабочего дня (API), считает опоздание от 09:00 | `user_id` | `TimeLogResponse` |
| `POST /web/clock-in/{user_id}` | То же самое, кнопка в кабинете сотрудника | `user_id` | redirect → `/dashboard/{user_id}` |

### 3.3 Заявки на отсутствие (`AbsenceRequest`) — **готов полностью**
| Метод/роут | Назначение | Вход | Выход |
|---|---|---|---|
| `POST /users/{user_id}/absences/` | Создать заявку (API) | JSON: `AbsenceCreate` | `AbsenceResponse` |
| `POST /web/request-absence/{user_id}` | Создать заявку (веб-форма) | form: `start_date`, `end_date`, `reason` | redirect → `/dashboard/{user_id}` |
| `POST /web/edit-absence/{request_id}` | Изменить даты/причину, только пока `PENDING` | form: `start_date`, `end_date`, `reason` | redirect → `/dashboard/{user_id}` |
| `POST /web/delete-absence/{request_id}` | Отменить заявку, только пока `PENDING` | `request_id` | redirect → `/dashboard/{user_id}` |
| `POST /web/approve-absence/{request_id}` | Одобрить (списывает `vacation_balance`, если хватает дней; иначе — ошибка) | `request_id` | redirect → `/admin` (+`?error=...` при нехватке дней) |
| `POST /web/reject-absence/{request_id}` | Отклонить (возвращает `vacation_balance`, если до этого была одобрена) | `request_id` | redirect → `/admin` |
| `GET /dashboard/{user_id}` | Кабинет сотрудника: профиль + форма заявки + список «Мои заявки» | `user_id` | HTML (`dashboard.html`) |
| `GET /admin` | Админ-панель: сотрудники, заявки на согласование, история решений, баннер ошибки | query: `error`, `err_user`, `err_needed`, `err_available` | HTML (`admin.html`) |

### 3.4 KPI-штрафы (`KPIPenalty`) — **модель есть, эндпоинтов и UI пока нет**
Таблица в `models.py` (`target_month`, `reason`, `penalty_percent`) существует, но ни один роут её не использует — раздел не реализован в текущем коде.

### 3.5 Косяки / дисциплинарные карточки (`Infraction`) — **не начато**
Только предложена схема модели (`SeverityEnum`: YELLOW/RED, поля `is_active`, `expires_at`, `removed_by`, `removed_at`), в `models.py` фактически ещё не добавлена. Роутов и шаблонов нет. Требуется решить вопрос сгорания карточек (см. раздел 1) перед реализацией.

## 4. Известные ограничения / технический долг

- 🔴 **Нет авторизации.** Любой может открыть чужой кабинет (`/dashboard/{любой_id}`), подменив ID в адресе. Критично для реального использования, некритично для тестирования в одиночку.
- 🟡 Нет проверки на **пересекающиеся даты** заявок одного сотрудника.
- 🟡 Нет запрета подавать заявку **задним числом** (дата начала в прошлом).
- 🟡 Нет **уведомлений** (email/в интерфейсе) о новых заявках или решениях — узнать можно только зайдя на страницу.
- 🟡 Модуль `KPIPenalty` — модель в БД есть, но не подключена нигде в `main.py`/шаблонах.
- 🟡 Модуль «Косяки» — не реализован, ждёт решения по бизнес-логике сгорания карточек.
- 🟢 Нет системы миграций БД (Alembic) — при изменении схемы `models.py` в проде потребуется ручной подход, не автоматический `create_all`.
- 🟢 Ошибки на редиректах передаются через query-параметры — рабочее, но негибкое решение; при добавлении новых сценариев ошибок стоит подумать о более общем механизме (например, flash-сообщениях через cookie/сессию).
